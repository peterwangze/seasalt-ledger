# 记账产品功能调研与迭代取舍

调研时间：2026 年 10 月  
目的：为「海盐账本」的月度/年度统计、本地优先能力和后续原生封装提供功能参考，而不是盲目堆功能。

## 1. 市场观察

参考的横评与产品资料：

- [少数派：16 款安卓个人记账 APP 大横评（2025-04）](https://sspai.com/post/98549)：对随手记、鲨鱼记账、钱迹、一木、薄荷、小星、Bluecoins 等 16 款产品的 77 个项目做了功能对比。
- [什么值得买：记账 App 横评（2026-06）](https://post.smzdm.com/p/a5rvzq23/)：强调快速记账、模板与长期可用性。

横评中出现频率较高的能力可以归为六组：

| 能力组 | 代表产品中的表现 | 用户价值 |
| --- | --- | --- |
| 记账效率 | 模板记账、周期记账、快捷分类、智能预选账户 | 降低每笔记录的操作成本 |
| 统计洞察 | 收支走势、分类占比、日历视图、资产走势、年度/期间选择 | 从「记了」变成「看懂」 |
| 预算 | 总预算、分类预算、收入预算、期间预算 | 控制消费，而不是事后复盘 |
| 账户/资产 | 信用卡、借贷、投资、多币种、账户余额 | 管理资产而不只是流水 |
| 内容组织 | 标签、商家、项目、二级分类、备注、图片、账单拆分 | 让检索和复盘有维度 |
| 安全与可用性 | 密码/手势/指纹、云同步、多账本、导入导出、小组件、深色模式 | 长期使用和换机安全感 |

其中，**日历视图、分类占比、收支走势、预算、导入导出**几乎是中高分产品的共同能力。年度/期间统计和资产视角常被放在「统计」而不是首页。

### 几个代表产品的侧重点

| 产品 | 值得借鉴的地方 | 对海盐账本的启发 |
| --- | --- | --- |
| 钱迹 | 资产走势、日历视图、周期记账、标签、多平台、体积小 | 统计要能进入长期视角；基础能力可以做得轻 |
| 一木记账 | 模板、周期、资产/借贷/投资账户、日历、标签、多账本 | 高频动作和长期资产是进阶方向，不应挤进首页 |
| 薄荷记账 | 智能预选、商家/项目标签、分账户标签预算、日历 | 分类快捷入口和清晰统计比堆设置更重要 |
| 鲨鱼记账 | 模板、周期、日历视图、分类预算（较多为付费） | 用户从鲨鱼迁移过来时，年度/日历/预算要能承接预期 |
| 随手记 | 多账本、预算、报表、日历、多人共享 | 多账本/共享需要账号体系，暂不适合本地优先版本 |
| Bluecoins | 丰富的统计图表、日历、资产走势 | 图表数量不等于洞察，应优先把月/年/周关系做清楚 |

## 2. 对海盐账本的取舍

海盐账本坚持三个前提：本地优先、无账号、轻量可安装。因此本轮不追求一次做成「功能大全」，优先解决以下高价值问题：

### 本轮已实现

1. **导入从首页移到「我的」**
   - 导入是一次性低频动作，不应该占据日常首页。
   - 首页的日常入口改为快捷分类和账单日历。

2. **统计升级为月度 / 年度双模式**
   - 月度：分类占比、每周趋势、分类排行、日历入口。
   - 年度：年收支总览、同比、12 个月走势、年度分类占比、年度排行和文字小结。
   - 与市场产品一致，把「年度复盘」作为统计的子模式，而不是首页常驻。

3. **账单日历**
   - 按天查看账单、用颜色表达支出强度、点选某天查看明细。
   - 支持直接从某一天补记，保存后回到该天。
   - 对应横评中反复出现的「日历视图」需求。

4. **快捷分类**
   - 首页直接展示高频支出分类，轻点后带着分类进入记账页。
   - 这是对「模板记账/快捷记账」的轻量实现，不引入复杂的模板管理。

5. **预算提示更实用**
   - 除总预算和进度外，增加「剩余天数」与「日均可用」。
   - 暂不引入分类预算，避免在数据模型和编辑复杂度上过早膨胀。

6. **为原生封装做布局调整**
   - 移除首页低频导入入口，压缩首屏层级。
   - 放大正文、辅助文字、触控目标与底部导航。
   - 针对高度较小的设备切换更紧凑的快捷入口。
   - 生产构建使用相对资源路径，适配 WebView/本地包加载。
   - 表格页、日历页统一处理安全区和键盘遮挡。

### 暂不做的功能（阶段规划）

这些功能在市场产品中很常见，但会显著增加存储、权限或交互复杂度；建议按原生版本节奏分阶段加入：

- 周期账单/自动记账：需要后台调度、通知权限、原生提醒。
- 分类预算/期间预算：需要预算模型和预算结转规则。
- 账户余额与资产曲线：需要账户初始余额、信用卡/借贷类型和转账语义。
- 多账本/多人共享/云同步：需要账号体系与同步冲突处理，和当前「本地优先」定位冲突。
- 标签、图片附件、报销：会扩大数据模型与存储体积。
- 密码/生物识别：更适合交给原生容器实现，而不是在 Web 层伪装安全。

## 3. 结论

市面产品已经把「记账」从流水记录推进到**洞察、预算和资产管理**：

- 统计需要同时有短周期和长周期视角；
- 日历是理解「某一天发生了什么」的最自然入口；
- 快捷记一笔比在首页放低频功能更重要；
- 对于本地优先产品，导入/导出和可恢复性比云同步更应优先做扎实。

本轮选择的是「不牺牲轻盈感的功能扩展」：把年度复盘、日历和快捷分类做进现有体验，同时保持无需账号、无需网络、随开随记。

## 4. v1.2.0 复盘：大账本、计算器与随手记迁移

这一轮直接基于 6 年账单试用反馈，重点不再是继续加页面，而是解决「长期使用后的手感」。

### 4.1 易用性观察

- **快速记账的路径要短**：鲨鱼记账和随手记都把高频分类、日期和账户放在第一屏；金额输入必须能处理「午饭 28 + 咖啡 19」这种心算场景。金额键盘直接支持 `+ − × ÷` 并实时显示结果，比先算好再输入更接近真实记账动作。
- **长期用户需要累计视角**：月度看节奏，年度看复盘，但使用数年后还需要「这几年一共花了多少、收入多少、结余多少」。因此统计增加「全部」模式，而不是把累计数据塞进年度页。
- **大账本要感觉轻**：六年账单导入后，首屏不应一次挂载整月几百条 DOM；分天懒加载、月/年索引和列表离屏渲染，能显著降低切换「明细」时的长任务。
- **迁移是留存入口**：随手记常见导出列是 `日期, 收支, 分类, 子分类, 金额, 备注, 账户, 成员, 项目`，其中「子分类」比一级分类更有意义；导入器优先识别子分类，并保留账户和备注。
- **本地优先是差异点**：不为了对齐云产品而引入账号、同步和多账本；先把导入、备份、恢复和离线体验做扎实。

### 4.2 本轮落地

| 反馈 | 实现 |
| --- | --- |
| 明细卡顿 | 月/年/日索引缓存；明细按 10 天分批显示；`content-visibility` 延迟离屏日期组；13k 条合成数据下导航长任务从约 81ms 降至 0 |
| 记账要能加减 | 四列计算器键盘，支持 `+ − × ÷`、运算优先级、实时结果、最多两位小数；保存时写入计算结果 |
| 全部账单统计 | 「全部」统计模式：累计收支/结余、跨年区间、年度走势、累计分类占比与排行 |
| 随手记导入 | 自动识别来源；支持 `子分类 / 二级分类`、`收支`、`成员`、`项目` 等列；增加随手记导出教程 |
| 继续优化 | 保留高频分类快捷入口，导入与备份仍放在「我的」，不挤占首页 |

### 4.4 仍然不做

- 周期账单和通知：需要原生后台调度与通知权限，先不伪装成 Web 能力。
- 多账本、多人共享、云同步：与本地优先定位冲突，等有明确需求再做。
- 复杂资产曲线和分类预算：需要新的账户余额、信用卡和预算结转模型，优先保证当前账本稳定。

v1.2.0 的原则仍然是：**不牺牲轻盈感地解决长期使用的真实摩擦**。
